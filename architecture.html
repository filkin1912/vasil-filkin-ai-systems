Commerce support assistant

Architecture for an authenticated customer message, an order lookup, and a refund ledger the model cannot rewrite.

Python FastAPI Pydantic LangGraph Tool calling Mock model In-memory ledger

1 The job

A customer is already signed in. They send one message. The assistant may describe their order and may record a refund. The amount has to come from the order line.

The model is allowed to choose a tool and to write the sentence. It is not allowed to choose the customer, the payable amount, or whether an inaccessible order exists.

One turn

1. Bind the authenticated customer id. Drop a customer id if the model sends one.
2. Planner sees the message and this customer's open proposals. It does not see the catalog.
3. Tools read one order, or ask the policy to quote or confirm.
4. Policy recomputes the item, the quantity, the amount, and whether to pay, from the message and the order.
5. Draft model receives only the decision fields it is allowed to say.
6. Grounding keeps the draft, or replaces it with a template and stores the draft for review.

SituationResult
Their order, asking where it isStatus, plus tracking when the order has it. No ledger row.
Delivered, one damaged unit, "can I"Proposal for unit_price × quantity. Nothing is submitted.
Order id is on another accountSame answer as a missing order. No item, name, email, or total.
Return received, they name a different amount and say processProposal for the line amount. Their figure is repeated and not paid.
They confirm that ledger amountOne executed refund. The same confirmation returns that refund.
"yes" with two open proposalsAsk which amount. No payment.
In transit, even if the message says it arrived brokenNo refund. The tracking number is the answer.
The idempotency key is customer, order, item, quantity, reason, and amount. A second submit with the same key does not create a second refund.

4 Technologies, and why

ChoiceWhy it is here
PythonThe support services I ship are Python. The mock, the policy, and the agent stay in one process a reviewer can run.
FastAPIThe brief asks for the simplest local interface. POST /support/messages is that interface. The script calls the same service object, so the HTTP layer is thin.
PydanticThe planner must return a known hint, and the draft must return {"reply": "..."}. A payload that does not parse is discarded.
LangGraphThe turn is a state graph with one branch: tools were requested, or they were not. That graph is what I would keep when the mock model is replaced. It does not loop.
DecimalSeed money is parsed from the JSON token and quantized to cents. The payable amount is the line, not a binary float and not the number in the chat.
Mock modelThe brief gives no credit for a paid model. MockModel.complete() reads the same messages a live model would read. OpenAICompatibleClient.payload() is the real request, and complete() refuses to send it.
In-memory storeRequired. Seed files are opened read-only. Clearing runtime state, or starting a new process, restores them. The mock stores untyped dicts. The refund shape lives in support/ledger.py.

Left out on purpose

Left outReason
Vector searchFour orders are a ledger, not a document corpus. An amount has to be the order line, so the path is a tool, not a retrieved paragraph.
PostgreSQL, Redis, Docker, KubernetesThe brief requires memory-only state and does not ask for a deployment. Those are the next place the ledger and the proposal TTL would go.
A user interfaceThe brief says not to spend the time box on one. The script and the one POST route are enough to exercise the agent.
A live OpenAI or OpenRouter callSame contract, no network. The production path I would add is a primary client and a timeout fallback, both behind ModelClient, with this policy unchanged.
An older chatbot of mine put the whole catalog in the prompt and let the model filter it. That is a poor fit here: a wrong euro amount would be a payment. The split on this page is the one I use when a number has to come from a verified row.
